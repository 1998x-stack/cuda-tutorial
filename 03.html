GPU 硬件架构概览

把 GPU 当成“更快的 CPU”来写代码，是初学者最常见的错误。打开引擎盖，先看清 SM、内存层次、warp 调度与 Tensor Core 这些真实的执行单元。

01 · 别把 GPU 当更快的 CPU

环境已经搭好，nvcc --version 也能输出了。但在写第一行 CUDA 代码之前，先回答一个问题：GPU 内部到底长什么样？

常见误区是把 for 循环拆成线程，以为“线程越多越快”——结果常常不达预期甚至更慢。原因在于 CPU 与 GPU 的设计哲学不同：CPU 用少量强大的核心降低单线程延迟，GPU 用大量简单核心换取吞吐。不理解硬件就往上堆代码，等于蒙着眼开车。这一章按“一个 SM 里有什么 → 各级内存多快 → 不同设备支持什么特性 → warp 怎么被调度 → 专用单元做什么”的顺序展开。

本章主线： 结构（SM）→ 存储（内存层次）→ 特性开关（计算能力）→ 执行（warp / SIMT）→ 加速器（Tensor Core）。每一步都回答一个“为什么这样写才快”的问题。

02 · SM 内部结构

GPU 的核心构成单元是 SM（Streaming Multiprocessor，流式多处理器）。可以把 SM 理解为一台“迷你计算单元”：内部有自己的 warp 调度器、寄存器文件、CUDA 核心、共享内存，以及可选的 Tensor Core。一整颗 GPU 由几十到数百个 SM 并行组成，这就是它算力惊人的来源。

组件作用对开发者的意义
Warp 调度器每周期挑选一个就绪 warp 发射指令一个 SM 有多个调度器，可用别的 warp 填补等待延迟的空档
CUDA Core执行标量浮点/整数运算kernel 里大部分算术指令在这里执行
Tensor Core专用的小矩阵乘累加单元AI/HPC 场景吞吐远高于 CUDA Core
寄存器文件SM 内最快的存储，供其上线程使用数量固定，用多了会 spilling，性能断崖
L1 / 共享内存低延迟片上存储，可配置为缓存或共享内存用好共享内存是优化核心（第 8 章）
一个关键数字： CC 8.0 每个 SM 有 65536 个寄存器。若每线程用 64 个，2048 个线程就要 131072 个——超出部分只能溢出到更慢的存储，性能可能掉一个数量级。所以“降低每线程寄存器用量”是长期有效的优化方向。

03 · 内存层次全景

内存层次是理解“为什么 GPU 编程需要特殊技巧”的核心。从最快到最慢，跨越了寄存器和全局内存之间两个数量级的差距。

内存类型延迟（量级）作用域容量
寄存器~1 cycle单线程255 个/线程（上限）
共享内存~5 cycles单 block~48–164 KB/SM
L1 缓存~5–10 cycles单 SM~128–256 KB/SM
L2 缓存~200 cycles整颗 GPU~6–40 MB
全局内存~400–800 cycles所有线程 + Host~4–80 GB

记住一个原则：让数据尽量待在高速存储里——能进寄存器就进寄存器，需要线程间共享就放共享内存，最后才落到全局内存。这条原则贯穿 CUDA 优化的始终。

大数组的陷阱： 在 kernel 函数里声明一个大数组，表面上像是“栈上变量”，编译后它很可能被放到 local memory——而 local memory 物理上位于全局内存，延迟比寄存器高两个数量级。用 --ptxas-options=-v 编译可以看到寄存器与 spill 统计。

04 · 计算能力（Compute Capability）

计算能力（Compute Capability，CC）用 主版本.次版本 表示，如 8.0、8.9。它不是“算力”指标，而更像一组 Feature Flag：告诉编译器与运行时这块 GPU 支持哪些硬件特性。下面是最主要架构的 CC 映射：

架构CC代表设备关键新特性
Tesla1.0G80CUDA 诞生
Fermi2.0GTX 480 / 580ECC、真正的 C++ 类/继承
Kepler3.0 / 3.5GTX 680 / K20Dynamic Parallelism、Hyper-Q
Maxwell5.0 / 5.2GTX 980 / M40共享内存与 L1 分离
Pascal6.0 / 6.1GTX 1080 / P100Unified Memory、NVLink
Volta7.0V100Tensor Core 1 代、独立线程调度
Turing7.5RTX 2080 / T4RT Core
Ampere8.0 / 8.6 / 8.9A100 / RTX 30903 代 Tensor Core、MIG、BF16、TF32、稀疏化
Ada Lovelace8.9RTX 40904 代 Tensor Core、FP8
Hopper9.0H100 / H200Transformer Engine、DPX、TPC
Blackwell10.0B200 / B100双芯片设计、FP4、5 代 NVLink

用 nvcc -arch=sm_XX 指定目标架构（如 A100 用 -arch=sm_80）。要兼容多种 GPU，可用 -gencode 同时生成多个架构的 cubin（二进制）与 PTX（中间代码），让驱动在运行时挑选最合适的版本。

兼容方向是单向的： 为较低 CC（例如 7.0）编译的代码可以在更高 CC 的 GPU 上运行；反过来不行。发布库给未知用户时，通常选较低的 CC 作为目标以覆盖更多设备。

05 · Warp 与 SIMT 发散

接下来是最核心也最容易被误解的概念：Warp。一个 warp 由 32 个线程组成，是 GPU 调度与执行的最小单位。你启动的成千上万个线程，在硬件层面按 threadIdx 每 32 个连续线程被组织成一个 warp。调度器每个周期挑选一个就绪 warp，发射一条指令——这 32 个线程同时执行同一条指令、操作各自的数据。

这就是 SIMT（Single Instruction, Multiple Threads）模型。与 CPU 的 SIMD 不同，SIMT 允许每个线程拥有自己的寄存器和执行路径。而这恰恰埋下了一个陷阱——warp divergence（分支发散）：

// 同一个 warp 内的线程走了不同的分支
__global__ void divergence_kernel(float *data, int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) {
        if (data[idx] > 0.0f) {
            data[idx] = sqrtf(data[idx]);   // 路径 A：正数
        } else {
            data[idx] = 0.0f;               // 路径 B：非正数
        }
    }
}

当同一个 warp 内有的线程走 then、有的走 else，硬件无法在同一周期执行两条路径，只能串行化：先执行路径 A 并屏蔽走 B 的线程，再执行路径 B 并屏蔽走 A 的线程。名义上是“并行 32 路”，实际有效吞吐减半。

有效吞吐≈ 1串行路径数

当同一 warp 内出现 k 条不同的分支路径时，它们被串行执行，有效吞吐约为 1/k。（教学示意；真实的开销还受指令数、掩码与调度影响。）

动手估一估：分支模式如何影响吞吐

选择一种分支情形，看看一个 warp 的有效吞吐会掉到多少。

不是让你别写 if： 若一个 warp 的 32 个线程都走同一分支，就不产生任何损失。问题只出在同一 warp 内走不同分支。因此一个常见优化思路是让同一 warp 内线程的数据模式保持一致——社区称之为 “warp-coherent” 编程。有一个真实案例：团队把按类别排序的数据重新排列，使同类别数据连续，从而让每个 warp 走同一分支，性能提升了约 40%。

06 · Tensor Core

Tensor Core 可能是过去十年 GPU 架构中最重要的创新。它专为矩阵乘累加 D = A × B + C 设计，在 Volta（V100）中首次引入，此后每一代都大幅增强。

它与 CUDA Core 的工作方式不同：CUDA Core 每次算一个标量操作，而 Tensor Core 一次完成一个小矩阵的乘法。这种“一次性搞定一小块矩阵”的能力，使其吞吐量可达同代 CUDA Core 的 8～16 倍（取决于精度）。

Tensor Core 不会自动启用，需要在代码中显式使用，常见有两种途径：

  • 直接编程：通过 CUDA C++ 的 warp 矩阵函数（nvcuda::wmma 命名空间）手动调用，适合需要精细控制的场景。
  • 通过 cuBLAS / cuDNN 等库：多数情况下你不必直接写 Tensor Core 代码，库在底层已经替你完成了。
精度是另一维旋钮： Tensor Core 支持 FP16、BF16、TF32、INT8/INT4、FP8 等多种精度；精度越低吞吐越高，但要评估对数值精度与收敛的影响。TF32 常被视为“甜点”：在 A100 上其 Tensor Core 吞吐约为 FP32 CUDA Core 的 8 倍，而精度损失很小。

到这里，我们已经看过了 SM、内存层次、计算能力、warp 调度与 Tensor Core。有了这些硬件知识，下一章终于可以写第一个真正的 CUDA kernel——一个简单的向量加法；它不长，但将是你亲手写下的第一段在 GPU 上并行执行的代码。
