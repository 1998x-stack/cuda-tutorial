线程层次结构

CUDA 的线程不是一根循环变量，而是一棵三维的树。搞清 Grid、Block、Thread 的从属关系与索引公式，就解决了 CUDA 编程里最容易出错的一半细节。

01 · 为什么不用一个循环变量

上一章我们写了第一个 CUDA 程序——向量加法。你肯定注意到了那一行 int idx = blockIdx.x * blockDim.x + threadIdx.x;。对初学者来说，这是全程序最令人困惑的表达式：blockIdx 是什么？threadIdx 又是什么？为什么不能像 CPU 那样写一个 for 循环，用简单的 i 递增？

答案在于：GPU 上成千上万个线程是同时执行的，没有一个“共享的循环计数器”。CPU 串行代码里，循环变量 i 由唯一的执行流推进；而 GPU 上每个线程都独立运行同一段 kernel，它必须能自己算出“我该处理哪一份数据”。这个“自己算出来”的身份，就由线程层次结构提供。

更麻烦的是：CUDA 的索引错误不会触发编译错误，只会悄悄产出错误的结果，甚至在越界时静默损坏别的内存。所以这一章的目标很明确：让你能把任意一个 (grid, block) 配置下的全局索引，一次写对。

学习路径： 先用一张图看清三层嵌套（结构）→ 认识四个内置变量（工具）→ 推导一维索引公式（公式）→ 推广到 2D/3D → 最后处理边界这种工程细节。

02 · Grid / Block / Thread 三层结构

CUDA 把一个 kernel 启动时创建的所有线程，组织成三层嵌套：

Grid (网格)
  └── Block 0 (线程块)
  │     ├── Thread 0
  │     ├── Thread 1
  │     └── ...
  └── Block 1
  │     └── ...
  └── ...

三层各自的角色并不相同，这一点直接决定了你后面能用哪些优化手段：

  • Thread（线程）：最小的执行单元。所有线程跑同一段 kernel，但通过各自的索引操作不同的数据。
  • Block（线程块）：一组线程的集合。只有同一个 block 内的线程才能互相协作——通过共享内存交换数据、用 __syncthreads() 同步（见第 7 章）。
  • Grid（网格）：一次 kernel 启动对应的全部 block 集合。
为什么 block 是协作的边界？ 因为 block 内线程会被调度到同一个 SM（流多处理器）上，硬件才保证它们的共享内存和 __syncthreads() 有效。不同 block 之间不保证同时驻留、不保证执行顺序，因此不能用 block 间同步来传递中间结果。

03 · 四个内置变量

每个线程靠四个内置变量来定位自己。注意 blockDim 和 gridDim 描述的是维度大小（有多少），而 threadIdx 和 blockIdx 描述的是当前下标（第几个）——四者恰好两两成对。

内置变量类型含义取值范围
threadIdxdim3线程在其所属 block 内的索引[0, blockDim-1]
blockIdxdim3block 在 grid 内的索引[0, gridDim-1]
blockDimdim3每个 block 的线程数由启动配置第二个参数指定
gridDimdim3每个 grid 的 block 数由启动配置第一个参数指定

每个变量都有 .x、.y、.z 三个分量。即使你只用一维，未使用分量的值也是 1 而不是 0——这是最常见的笔误来源之一。

04 · 一维索引计算

绝大多数入门场景是一维的：处理一个一维数组，启动一维的 grid 和 block。此时全局索引由下面的公式给出——它是整个 CUDA 编程中被写得最多的一行：

idx= blockIdx.x× blockDim.x+ threadIdx.x

逐项拆开看，每一项都有明确的物理含义：

  • blockIdx.x：当前是第几个 block（从 0 开始）；
  • blockDim.x：每个 block 里有多少个线程；
  • blockIdx.x * blockDim.x：在当前 block 之前，已经“排过队”的线程总数；
  • + threadIdx.x：再加上当前线程在 block 内的偏移，就得到全局唯一索引。

把公式放进完整的向量加法里，再加上必要的越界保护：

// 1D 向量加法的完整例子
__global__ void vecAdd(float *a, float *b, float *c, int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) {              // 越界保护，见第 07 节
        c[idx] = a[idx] + b[idx];
    }
}

// 启动配置
int n = 1000000;
int blockSize = 256;
int gridSize = (n + blockSize - 1) / blockSize;  // 向上取整 = 3907
vecAdd<<<gridSize, blockSize>>>(d_a, d_b, d_c, n);

动手算一算：从 (blockIdx, threadIdx) 得到全局索引

改动下面的数字，或点击“下一个例子”在预设场景间切换，观察 idx 如何随三个量变化。所有数值都是整数算术的演示。

05 · 二维与三维索引

很多问题天然是二维或三维的——图像（高 × 宽）、物理网格（x/y/z）、矩阵（行 × 列）。CUDA 允许你用 2D 或 3D 的 grid/block 去匹配问题的维度，让索引写起来更自然，也让块内线程的空间局部性更直观。

// 2D grid/block —— 适合矩阵 / 图像
__global__ void matrixAdd(float *a, float *b, float *c, int width, int height) {
    int col = blockIdx.x * blockDim.x + threadIdx.x;  // x 方向 → 列
    int row = blockIdx.y * blockDim.y + threadIdx.y;  // y 方向 → 行

    if (col < width && row < height) {
        int idx = row * width + col;   // 展平为 1D 索引
        c[idx] = a[idx] + b[idx];
    }
}
// 启动: dim3 blockDim(16, 16); dim3 gridDim((w+15)/16, (h+15)/16);
// 3D grid/block —— 适合体数据 / 三维网格
__global__ void volumeProcess(float *data, int dx, int dy, int dz) {
    int ix = blockIdx.x * blockDim.x + threadIdx.x;
    int iy = blockIdx.y * blockDim.y + threadIdx.y;
    int iz = blockIdx.z * blockDim.z + threadIdx.z;

    if (ix < dx && iy < dy && iz < dz) {
        int idx = (iz * dy + iy) * dx + ix;  // 行优先展平
        // 处理 data[idx] ...
    }
}
// 启动: dim3 blockDim(8, 8, 8); dim3 gridDim(dx/8, dy/8, dz/8);
x 是“最快”的维度。 在展平里，x 方向相邻的线程对应数组里相邻的下标，因此 2D 上也应让 threadIdx.x 对齐内存中连续的方向，才能得到合并访问（第 6 章）。把 x/y 搞反会让全局内存访问效率成倍下降。

06 · Block 大小的选择

block size（每个 block 的线程数）是 CUDA 世界里被问得最多的问题。它没有唯一正确答案，但有几条硬约束和一组经验值。先说硬约束：

  • 必须是 32 的倍数。 硬件以 warp（32 线程）为单位调度；block 不是 32 的整数倍时，最后一个 warp 会出现“空槽”，硬件仍按整 warp 分配资源。
  • 每块最多 1024 个线程。 计算能力 ≥ 2.0 的设备统一如此。
  • 每个维度还有上限。 maxThreadsDim 通常是 1024 × 1024 × 64。

在满足硬约束之后，选择 block size 更像一场取舍：

Block Size优点代价适用场景
128灵活，SM 上可容纳较多 block单块工作量较少通用场景的稳妥选择
256计算与访存较均衡寄存器压力略升最常用的默认值
512块内协作空间更多可能限制每 SM 活跃 block 数共享内存使用较多的 kernel
1024单块线程数拉满寄存器预算紧张，易 spill寄存器需求低、共享内存密集的 kernel

还有一个关键概念是占用率（occupancy）——每个 SM 上活跃 warp 数与硬件上限之比。占用率越高，SM 用并行掩盖访存延迟的能力通常越强；但占用率不等于性能：计算密集的 kernel 用较低的占用率也可能跑满吞吐。这个权衡会在第 17 章展开。

经验法则： 从 blockSize = 256 起步，它兼顾了足够的可调度线程与合理的每 SM block 数量（例如 A100 计算能力 8.0 每 SM 最多驻留 32 个 block）。随后再试 128、512、1024，以实测为准。

07 · 边界检查与网格跨度循环

数据量往往不是 block size 的整数倍。以 n = 1000000、blockSize = 256、gridSize = 3907 为例，最后一个 block 只有 1000000 - 3906×256 = 64 个有效元素，其余 192 个线程会越界。这就是 if (idx < n) 存在的理由——它不是可选项。

另一种常见做法是让每个线程处理多个元素，即网格跨度循环（grid-stride loop）：

// 网格跨度循环 —— 每个线程处理多个元素
__global__ void vecAdd_stride(float *a, float *b, float *c, int n) {
    int stride = gridDim.x * blockDim.x;          // 总线程数作为步长
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    while (idx < n) {                             // 每轮前进一个 stride
        c[idx] = a[idx] + b[idx];
        idx += stride;
    }
}
// 启动：blockSize = 256, gridSize = 128（远小于需要的 3907）
  • 适应任意数据量：不必让 grid/block 精确整除 n；
  • 负载更均衡：每个线程处理的工作量大致相同；
  • 便于调试：先用少量线程跑通逻辑，再放大规模，kernel 逻辑不必改。
越界写入最危险的地方在于它“不报错”。 若越界写到别的有效数据上，程序常常照常运行、结果却悄悄变错，且随机复现。所以两件事要养成肌肉记忆：每个内存访问都在心里核对边界，每次 CUDA API 调用都检查返回值。
