同步机制入门

前面的内核里线程各自为战；一旦线程需要交换数据，“谁先写完、谁后读到”就成了正确性问题。这一章讲清块内屏障 __syncthreads()、最容易踩的条件分支陷阱，以及 Host 与 Device 之间的同步粒度。

01 · 为什么需要同步

之前几章的内核都很简单：每个线程独立工作、互不依赖。但现实中的并行计算很少这么“老死不相往来”——大部分时候线程需要协作。而一旦协作，就引出了并发编程里最麻烦的问题：同步。

如果你写过 pthread 或 Java 多线程，对“竞态条件”和“死锁”不会陌生。GPU 上的同步问题比 CPU 上更隐蔽：成千上万个线程同时在跑，调试器很难介入，而且很多同步错误不是每次都能复现。这一章系统讲清三件事——块内同步、Host/Device 同步，以及什么时候不需要同步。

02 · __syncthreads() 块内同步

__syncthreads() 是CUDA中最基本的同步原语。它的作用是：在同一个block内的所有线程到达这个"路障"之前，没有任何线程能越过它继续执行。你可以把它想象成一个接力赛的交接棒点——所有队员必须在交接点集齐，才能一起出发跑下一段。

最经典的使用场景是：将全局内存中的数据加载到共享内存，所有线程都加载完毕之后，再统一开始计算。

// __syncthreads() 的典型用法 —— 共享内存的生产者-消费者模式
__global__ void syncthreads_example(float *input, float *output, int n) {
    // 声明共享内存（每个block一份）
    __shared__ float s_data[256];

    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    int tid = threadIdx.x;

    // 阶段1: 所有线程并行地从全局内存加载到共享内存
    if (idx < n) {
        s_data[tid] = input[idx];
    } else {
        s_data[tid] = 0.0f;  // 边界填充
    }

    // 屏障：确保上一步的加载全部完成
    // 在此之后，任何线程都可以安全地读取 s_data 中其他线程写入的值
    __syncthreads();

    // 阶段2: 所有线程从共享内存读取数据并进行计算
    // 注意这里可能读取相邻线程写入的 s_data 元素
    float sum = 0.0f;
    #pragma unroll
    for (int i = 0; i < 5; i++) {
        int neighbor = (tid + i) & 255;
        sum += s_data[neighbor];
    }

    if (idx < n) {
        output[idx] = sum;
    }
}
关键理解： 没有 __syncthreads()，线程 A 写入共享内存的数据，线程 B 不一定能读到——因为 A 可能还没写完，B 就已经开始读了。这种“读未写完”的错误在 CPU 多线程里也会出现，但 GPU 的 warp 调度使它更难预测和复现。

03 · 条件分支中的陷阱

这是 CUDA 同步中最经典、最致命、最容易犯的错误。看下面的代码：

// 错误的做法 —— __syncthreads() 在条件分支中
__global__ void broken_sync(float *data, int n) {
    __shared__ float s_buf[256];
    int tid = threadIdx.x;

    if (tid < 128) {
        // 只有前128个线程执行这部分
        s_buf[tid] = data[tid];
        __syncthreads();  // ❌ 危险！不是所有线程都到达这个屏障
    }

    // 所有线程执行这部分
    float val = s_buf[(tid + 64) & 255];  // 可能读到未初始化的值
    data[tid] = val;
}

// 正确的做法 —— __syncthreads() 必须在所有线程可达的位置
__global__ void fixed_sync(float *data, int n) {
    __shared__ float s_buf[256];
    int tid = threadIdx.x;

    // 先做条件赋值
    if (tid < 128) {
        s_buf[tid] = data[tid];
    } else {
        s_buf[tid] = 0.0f;
    }

    // 屏障在条件之外 —— 所有线程都能到达
    __syncthreads();  // ✅ 安全

    // 然后读取
    float val = s_buf[(tid + 64) & 255];
    data[tid] = val;
}
__syncthreads() 在条件分支中 = 未定义行为。 如果块内一部分线程进入了条件分支、另一部分没有，那么进入分支的线程会卡在屏障上等待——永远等不来那些根本没走进这个分支的线程，于是死锁：内核挂在那里，不结束、不报错，直到 Host 端超时。更麻烦的是，死锁不一定每次都发生——它取决于 warp 调度顺序，是典型的 Heisenbug。

真实的故事：有一次我写了一个卷积 kernel，用共享内存缓存输入数据，在加载后加了一个 __syncthreads()——但它被放在 if (tid < need_padding) 的条件分支里。用 256 线程的 block 测试时一切正常；换成 512 线程——内核直接死锁。排查了一整天，直到有人提醒：“你这个 __syncthreads 是不是跑偏了？” 把它移出条件分支，一切正常。从那以后我养成了一个习惯：写 __syncthreads 前先确认所有线程都能到达这里。

动手：屏障安全自检

如果带 __syncthreads() 的分支只有一部分线程会进入，其余线程就永远到不了屏障。输入 blockSize 与“会进入分支的线程数”，看看这段代码是否安全。

04 · Host-Device 同步

除了 block 内的线程同步，还有 Host 和 Device 之间的同步。CUDA 提供了几个不同粒度的同步函数：

函数 作用 粒度 性能影响
cudaDeviceSynchronize() 阻塞Host直到该设备上所有未完成操作完成 设备级 最大——暂停Host直到GPU全部完成
cudaStreamSynchronize(stream) 阻塞Host直到指定stream上的所有操作完成 流级 中等——只等一个流
cudaEventSynchronize(event) 阻塞Host直到特定事件完成 事件级 最小——只等一个点
cudaStreamWaitEvent(stream, event) 让指定stream等待一个事件（不阻塞Host） 流间 极小——纯GPU侧的同步
性能建议： 尽量减少 Host-Device 同步的频率。每次 cudaDeviceSynchronize() 都强制 CPU 等到 GPU 所有工作完成，破坏了流水线并行。理想情况下，只在需要确认结果或准备下一批数据时才同步；内核之间让 GPU 异步地自己链式执行，而不是 CPU 每启动一个内核就同步一次。这正是 CUDA 流（第12章）要解决的问题。

05 · 异步执行模型

理解 CUDA 的异步执行模型，是写出高效程序的关键。你可能以为下面的代码是顺序执行的：

// CUDA 的异步执行模型
kernel1<<<grid1, block1>>>(d_data1);
kernel2<<<grid2, block2>>>(d_data2);
cudaMemcpy(h_result, d_result, bytes, cudaMemcpyDeviceToHost);

但实际上：kernel的启动是异步的。CPU在调用 kernel1<<<>>>() 之后，不会等待它执行完毕，而是立即返回并继续执行下一条指令。kernel2 的启动也是异步的。cudaMemcpy 呢？它默认是同步的——CPU会阻塞在这里直到拷贝完成（除非你在两个支持异步拷贝的GPU之间用特殊API）。

所以，上面的代码实际执行流程是：

  1. CPU提交kernel1到GPU执行队列，立即返回
  2. CPU提交kernel2到GPU执行队列，立即返回
  3. CPU提交cudaMemcpy到GPU执行队列，然后CPU阻塞等待完成
  4. GPU按顺序执行：kernel1 → kernel2 → cudaMemcpy
// 显式展示异步执行
#include <stdio.h>
#include <cuda_runtime.h>

__global__ void simple_kernel() {
    printf("Hello from GPU thread %d\n", threadIdx.x);
}

int main() {
    printf("[Host] 准备启动kernel...\n");

    simple_kernel<<<1, 4>>>();

    printf("[Host] Kernel已启动（但可能还没执行！）\n");

    // 显式同步，确保GPU完成
    cudaDeviceSynchronize();

    printf("[Host] 同步完成\n");
    return 0;
}

// 可能的输出顺序：
// [Host] 准备启动kernel...
// [Host] Kernel已启动（但可能还没执行！）
// Hello from GPU thread 0
// Hello from GPU thread 1
// Hello from GPU thread 2
// Hello from GPU thread 3
// [Host] 同步完成
理解异步的重要性： 异步启动意味着 CPU “不等待”——GPU 在算的时候，CPU 可以去准备下一批数据、调度其他任务。这是实现计算与数据传输重叠的基础：让 GPU 读显存计算的同时，CPU 把下一批数据拷进显存；设计得当时，额外的传输时间可以被计算完全隐藏。这就是 CUDA 流（第12章）对高性能应用至关重要的原因。

06 · 同步的代价

同步不是免费的。每一次 __syncthreads() 都有性能开销：

  • 等待时间：快的warp必须等待慢的warp到达屏障。如果block内的warp之间负载不均衡，等待时间可能很长
  • 硬件代价：屏障需要硬件状态跟踪，占用SM的控制逻辑资源

但这不意味着要避免使用 __syncthreads()——该用时必须用，否则结果错误。好的策略是：

  • 尽量减少屏障次数：将需要同步的操作合并到一起，减少"同步-工作-同步-工作"的交替次数
  • 考虑warp级别编程：如果只需要同一个warp内的线程协作，可以用更轻量级的warp shuffle指令（第14章），它不需要显式同步
  • 负载均衡：让block内的所有线程做大致等量的工作，避免部分线程过早完成而空等
什么时候可以不用同步？ 如果块内每个线程完全独立工作（比如向量加法），不需要读其他线程写入的数据，那就完全不需要 __syncthreads()。很多人有一个误解——以为它是“每个内核都必须有的标配”。不是：只在需要线程间通信时才用，没有数据依赖的内核反而能跑得更快。

这一章我们理清了同步的基础：__syncthreads() 如何协调块内协作，条件分支里的屏障陷阱，Host-Device 的不同同步粒度，以及异步执行模型的含义。下一章我们把这块知识用起来，深入 CUDA 优化中最强大的工具之一——共享内存：它既是线程间通信的高速信道，也是把全局内存带宽利用率拉满的关键武器。
