共享内存深入

共享内存是程序员亲手管理的一块片上高速缓存：用得好，内核性能可以成倍提升；用不好，它比直接读全局内存还慢。关键就在“Bank”这个 32 路的硬件结构，以及一个只需多加一列就能解决的 Padding 技巧。

01 · 为什么共享内存立竿见影

如果你问一个用了五年 CUDA 的工程师：“GPU 上什么优化最立竿见影？”十有八九会得到同一个答案——共享内存（shared memory）。它是 CUDA 内存层次里的一颗明珠：由程序员亲手管理的片上缓存，延迟远低于全局内存。用好它，内核性能可以成倍提升；用不好、或者根本不用，内核可能连显存带宽的一小部分都用不到。

第 7 章我们已经用 __syncthreads() 配合共享内存做过块内协作，但那只是冰山一角。这一章深入它的本质：物理结构、Bank 冲突的来龙去脉、用 Padding 避免冲突，以及一个经典的分块矩阵乘法实战。

核心思想： 共享内存是“程序员管理的高速缓存”。用它减少对全局内存的访问——这是 CUDA 性能优化的第一条黄金法则。

02 · 分配方式回顾

先快速回顾一下共享内存的基本用法。在CUDA中，共享内存用 __shared__ 修饰符声明，它是每个线程块（block）私有的，同一个block内的所有线程都可以读写。有两种分配方式：

静态分配是在编译时确定大小的。你在内核函数内部直接声明：

__global__ void kernel_static() {
    __shared__ float cache[256];  // 编译时固定256个float
    // ...
}

动态分配则允许在运行时指定大小。声明时用 extern __shared__ 加上 []，然后在启动内核时用第三个尖括号参数传入大小（以字节为单位）：

__global__ void kernel_dynamic() {
    extern __shared__ float cache[];  // 大小由启动参数决定
    // ...
}

// 启动时指定共享内存大小（字节）
kernel_dynamic<<<grid, block, 256 * sizeof(float)>>>();

注意动态分配只能有一个 extern __shared__ 数组，如果要同时分配多个不同类型的数组，你需要手动计算偏移量。这是很多新手会踩坑的地方。

小贴士： 现代 CUDA 架构（Compute Capability 7.0+）允许通过 cudaFuncSetAttribute() 提高每个 block 可用的最大共享内存（默认上限及可选上限随架构与设备而变，例如较新的数据中心 GPU 可配置到 100KB 以上）。需要更多共享内存时务必显式调用该 API，否则 <<<>>> 参数里设再多也会被截断。

03 · Bank 与 Bank Conflict

共享内存之所以速度快，是因为它在硬件上被分成了32个存储体（bank），每个bank的宽度是4字节（32位）。这32个bank可以同时被访问——理论上，如果你的32个线程分别访问32个不同的bank，那么一次内存访问就能完成所有线程的请求。但如果两个（或更多）线程访问了同一个bank中的不同地址，就会发生bank conflict——这些访问会被串行化，性能随之下降。

下面这张表总结了不同的访问模式及其冲突程度：

访问模式 示例 Bank冲突程度 实际带宽利用率
所有线程访问同一地址（广播） s_data[0] 无冲突（硬件广播） 100%
线程i访问地址i（步长1） s_data[threadIdx.x] 无冲突 100%
线程i访问地址2i（步长2） s_data[threadIdx.x * 2] 2-way 50%
线程i访问地址4i（步长4） s_data[threadIdx.x * 4] 4-way 25%
线程i访问地址32i（步长32） s_data[threadIdx.x * 32] 32-way（最坏情况） 3.125%
随机访问 s_data[rand() % N] 高概率冲突 不可预测

一个很重要的细节：bank 编号是由地址计算出来的——对 32 位字（如 float），地址 addr 对应的 bank 编号是 (addr / 4) % 32。所以 s_data[0] 到 s_data[31] 恰好分属 32 个不同 bank，步长为 1 的访问完美对齐。但如果声明的是 __shared__ char s_data[128]，每个 bank 会包含 4 个字节，映射就不同了——这也是共享内存通常用 float / int 操作的原因之一。

bank=(⌊addr4⌋) mod 32
重要： Bank conflict 只发生在同一个 warp 内的线程之间。不同 warp 的线程访问共享内存不会相互冲突，因为 warp 是独立调度的。所以“32 个 bank”恰好对应一个 warp 的 32 个线程——这不是巧合，而是有意为之。

04 · Padding 技巧

当线程需要按列访问一个二维共享内存数组时，bank conflict 几乎是必然的。比如在一个 block 内处理 32 x 32 的矩阵，每个线程处理一行：

// 有 bank conflict 的版本：行号=threadIdx.x，列 j 固定
__shared__ float tile[32][32];

// 线程 threadIdx.x 读第 j 列
float val = tile[threadIdx.x][j];  // bank = (32·r + j) mod 32 = j → 32 个线程全撞同一个 bank

// Padding 版本：每行多开一个 float
__shared__ float tile_padded[32][33];  // 第二维用 33

// 同样的访问模式，这次无冲突
float val = tile_padded[threadIdx.x][j];  // bank = (33·r + j) mod 32 = (r+j) mod 32

为什么加一个 padding 就能消除冲突？因为对固定列 j，无 padding 时元素 tile[r][j] 的字地址是 32r + j，对应 bank (32r + j) mod 32 = j——与行号 r 无关，于是 32 个线程（不同 r、同一 j）全部命中 bank j，形成最坏的 32-way 冲突。换成 33 宽后，tile_padded[r][j] 的 bank 变成 (33r + j) mod 32 = (r + j) mod 32，随 r 逐一代开，冲突就消失了。代价只是每行多一个 float（128 行才多 512 字节），却是极其廉价又有效的优化。

口诀： 二维共享内存、按列访问时加 padding——多开一个元素，常常能省下成倍的访存时间。（下面的“加速倍数”类说法均来自教学示例，实际收益随访问模式与硬件而变。）

05 · 分块矩阵乘法

共享内存最经典的应用就是分块矩阵乘法（tiled matrix multiplication）。不用共享内存的朴素版本，每个线程需要多次读取全局内存来获取A和B的元素；而分块版本让同一block的线程协作：先把子矩阵从全局内存加载到共享内存，然后从共享内存读取数据进行计算。

#define TILE_SIZE 16

__global__ void matmul_tiled(float *A, float *B, float *C,
                              int M, int N, int K) {
    // 声明共享内存块
    __shared__ float As[TILE_SIZE][TILE_SIZE];
    __shared__ float Bs[TILE_SIZE][TILE_SIZE];

    int row = blockIdx.y * TILE_SIZE + threadIdx.y;
    int col = blockIdx.x * TILE_SIZE + threadIdx.x;
    float sum = 0.0f;

    // 遍历所有tile
    for (int t = 0; t < (K + TILE_SIZE - 1) / TILE_SIZE; ++t) {
        // 协作加载A的子块到共享内存
        if (row < M && t * TILE_SIZE + threadIdx.x < K)
            As[threadIdx.y][threadIdx.x] = A[row * K + t * TILE_SIZE + threadIdx.x];
        else
            As[threadIdx.y][threadIdx.x] = 0.0f;

        // 协作加载B的子块到共享内存
        if (col < N && t * TILE_SIZE + threadIdx.y < K)
            Bs[threadIdx.y][threadIdx.x] = B[(t * TILE_SIZE + threadIdx.y) * N + col];
        else
            Bs[threadIdx.y][threadIdx.x] = 0.0f;

        __syncthreads();  // 确保所有线程都加载完毕

        // 从共享内存读取并计算
        for (int k = 0; k < TILE_SIZE; ++k)
            sum += As[threadIdx.y][k] * Bs[k][threadIdx.x];

        __syncthreads();  // 防止下一轮覆盖时还有线程在读取
    }

    if (row < M && col < N)
        C[row * N + col] = sum;
}

这个kernel的关键步骤解析：

  • 第8-9行：每个block声明自己的 TILE_SIZE x TILE_SIZE 共享内存，用于缓存矩阵A和B的子块
  • 第17-22行：block内的 TILE_SIZE * TILE_SIZE 个线程并行从全局内存加载数据到共享内存。每个线程负责一个元素
  • 第24行：__syncthreads() 确保所有数据加载完成——这一步不能少，否则有些线程可能还没把数据写进共享内存，其他线程就开始读了
  • 第27行：从共享内存读取数据做乘累加。这里的 As[threadIdx.y][k] 和 Bs[k][threadIdx.x] 的访问模式是步长为1的——避免了bank conflict
  • 第29行：第二个 __syncthreads() 确保所有线程在下一轮覆盖共享内存前都已完成读取

对比朴素版本：对于 TILE_SIZE = 16，每个输出元素从共享内存读取 16 次（内层循环），但从全局内存只加载 1 次；而朴素版本每个元素要从全局内存读 16 次。共享内存的延迟量级远低于全局内存，性能差异也由此而来。

关键数量级： 在 A100 这一代，HBM 显存带宽约 2 TB/s（官方数据），而片上共享内存的聚合带宽可达其数倍——具体数值随 SM 数量与时钟而变化，这里只为说明“量级差异”，不作为基准。（教学示意）

06 · 用工具检测冲突

你怎么知道自己的共享内存访问有没有bank conflict？肉眼检查当然可以，但实际项目中的访问模式往往复杂得多。最可靠的方法是用NVIDIA Nsight Compute（ncu）进行profiling。

在Nsight Compute的Memory Workload分析部分，有一项叫 L1/Shared Memory Bank Conflicts 的指标。它会显示每个warp的平均bank conflict次数。理想值是0——意味着所有32个线程的访问都被完美调度。如果这个值接近warp大小（32），说明几乎是每个访问都在冲突，性能损失巨大。

一个真实踩坑故事（个人经历，非基准测试）： 几年前优化一个流体力学模拟内核时，我直觉认为“加共享内存肯定能加速”，于是把所有全局内存访问都换成了共享内存。结果内核反而变慢了。用 Nsight Compute 一查才发现：我的访问是按列读一个 __shared__ float data[32][32]，32 个线程恰好全命中同一个 bank，形成 32-way 全冲突。加了一列 padding（改成 [32][33]）后性能才回升。典型的好心办坏事：加了共享内存，却因为 bank conflict 而得不偿失。

这个故事说明：共享内存不是银弹。它确实快，但前提是你理解它的 bank 结构、并保证访问模式友好。一个简单的 padding 就能解决大部分问题；但更重要的是——永远不要假设优化有效，要用 profiler 数据说话。

动手：访问步长的冲突程度

一个 warp 的 32 个线程按下标 i 访问 s_data[i × stride]。输入 stride，看看落到几个 bank、最大冲突是几路。

日常检查清单： 使用共享内存后，顺手查三点——（1）访问模式是否步长为 1？（2）二维数组有没有按列访问？（3）Nsight Compute 的 bank conflict 计数是不是 0？三问全过，基本就没问题了。

这一章从共享内存的分配方式讲到 bank conflict 的硬件原理，从 padding 技巧讲到分块矩阵乘法，还记了一个踩坑案例。共享内存用好了，CUDA 编程就真正上了一个台阶。下一章我们谈另一个同样重要的话题——全局内存优化：它是 GPU 上最慢的内存，但很多人在写内核时根本没意识到自己的访问模式有多糟。
