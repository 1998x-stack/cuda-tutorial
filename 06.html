内存模型基础

在 GPU 上，计算几乎是“免费”的——一次乘加只要一两个周期；而一次全局内存访问要几百个周期。这一章要建立的直觉是：性能问题大多不是算得慢，而是等数据等得久。

01 · 为什么内存是瓶颈

有一个在 GPU 圈子里流传很广的说法：你 99% 的性能优化问题，归根结底都是内存访问问题。它背后的数量级差异是这样的——一个 FMA（融合乘加）指令消耗 1～2 个周期，而一次未命中的全局内存访问要 400～800 个周期。当线程把大部分时间花在等数据时，再多的并行也难以把吞吐填满。

所以这一章的顺序是：先建立内存层次的整体图景（结构），再看决定全局内存效率的合并访问（机制），然后讨论寄存器溢出与统一内存这两个高频工程话题，最后收在真实的内存错误上。

本章的读法： 不要把延迟数字当成精确标称去背——它们随架构变化。你要记住的是数量级：片上存储比显存快两个数量级，而“访问模式”能在同一块显存上造成数倍的效率差。

02 · 内存类型总览

CUDA 程序能访问多种内存，它们的差别主要落在三件事上：作用域（谁能看见）、生命周期（活多久）和速度（离计算单元多远）。

内存类型作用域生命周期速度（量级）大小说明
寄存器单线程线程~1 cycle255 个/线程 (CC 8.0)最快的存储，线程私有
局部内存单线程线程~400 cycles无硬上限（但很慢）寄存器溢出的“备胎”，物理上在全局内存
共享内存单 blockblock~5 cycles~48–164 KB/SMblock 内线程通信渠道，片上存储
全局内存所有线程 + Host程序控制~400–800 cycles数 GB 至 80 GB最大的存储池，也最慢
常量内存所有线程 + Host程序控制~5 cycles (cache hit)64 KB只读，硬件广播优化，适合所有线程读同一份数据
纹理内存所有线程 + Host程序控制~100–400 cycles取决于全局内存只读，专用缓存，适合空间局部性强的访问
黄金法则： 把频繁访问的数据尽量放到层次结构中靠近计算单元的位置。典型策略是全局内存 → 共享内存 → 寄存器，每一步都对应几十到几百倍的延迟差异。

03 · 全局内存与合并访问

全局内存最常用，也最慢。但并非所有全局访问都一样慢——关键在合并访问（coalesced access）。

当同一个 warp 的 32 个线程同时发出访问请求时，硬件会尝试把它们合并成尽量少的高效内存事务。若这 32 个线程访问的是连续地址（线程 0 读 a[0]、线程 1 读 a[1]……），一个 128 字节的事务就能覆盖全部访问；若地址彼此散开，硬件可能要为几乎每个线程单独开一个事务，效率随之成倍下降。

同样的数组、同样的运算，仅因访问模式不同，有效带宽会差出好几倍：

访问模式步长有效带宽（量级示意）效率
连续（合并）1~1550 GB/s100%
跨步2~775 GB/s50%
跨步4~387 GB/s25%
随机—~50–200 GB/s3–13%
表头为什么写“量级示意”？ 表中 ~1550 GB/s 是 A100 40GB 的标称 HBM 带宽量级（其数值随显存规格而变），而跨步行恰好折半、四分之一，是“事务数随 stride 线性增长”这一模型的理想示意，并非某次实测结果。你要带走的是成比例下降这个结论，而不是某个绝对值。

动手看一看：stride 如何决定事务数与效率

选择步长，观察一个 warp 的 32 次访问会落成多少个内存事务。模型假设：连续访问合并为 1 个 128B 事务；整数步长时事务数随 stride 成比例增加。

效率≈ 1stride

当 stride 取整数且访问对齐时，触及的 128B 事务数大致与 stride 成正比，因此效率约为 1/stride；随机访问退化到“几乎每线程一个事务”，效率降到个位数百分比。（教学示意）

// 合并访问 —— 高效
__global__ void coalesced_kernel(float *data, int n) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx < n) {
        data[idx] = data[idx] * 2.0f;   // t0→data[0], t1→data[1] ... 完美合并
    }
}

// 跨步访问 —— 低效
__global__ void strided_kernel(float *data, int n, int stride) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx * stride < n) {
        data[idx * stride] = data[idx * stride] * 2.0f;  // 地址间隔 stride，无法合并
    }
}
一个类比： 合并访问像推着车沿书架按编号取书——走一趟就取完；跨步访问像在书架间来回跳着各取一本——大部分时间花在跑动上，而不是看书。

04 · 寄存器与局部内存

寄存器是 GPU 上最快的存储，没有之一。每个线程可用的寄存器数量由硬件决定（例如 CC 8.0 上最多 255 个）。当 kernel 需要的寄存器超过上限，编译器会把溢出的部分溢出到局部内存（local memory）。局部内存物理上位于全局内存，速度相差两个数量级。

# 编译时查看寄存器统计
nvcc --ptxas-options=-v -arch=sm_80 -o mykernel mykernel.cu

# 输出示例：
# ptxas info: Used 32 registers, 8192 bytes smem, 320 bytes cmem[0]

寄存器用量还会反过来限制占用率：寄存器文件是 SM 上的固定资源，单个线程用得多，能同时驻留的线程就少。

算一笔账： CC 8.0 每个 SM 有 65536 个寄存器。若每个线程用 32 个寄存器，一个 SM 最多可容纳 65536 ÷ 32 = 2048 个线程；若每线程用 128 个，则只剩 512 个——占用率从 100% 降到 25%。这正是“降低寄存器使用量”常被列为优化目标的原因。
// 容易导致寄存器溢出的写法 —— 在 kernel 内声明大数组
__global__ void bad_kernel(float *data) {
    float temp[256];               // 需要的寄存器太多，被迫放进 local memory（慢）
    for (int i = 0; i < 256; i++) temp[i] = data[i * 1000];
}

// 更好的写法 —— 复用少量寄存器
__global__ void better_kernel(float *data) {
    float sum = 0.0f;              // 1 个寄存器，循环中反复使用
    for (int i = 0; i < 256; i++) sum += data[i * 1000];
}

降低寄存器用量的常用手段：把反复使用的子表达式提取为临时变量（编译器已做很多，手工有时仍有帮助）；用 -maxrregcount=N 强制限制每线程寄存器数（但压得太狠会增加 spill，反而更慢）；用共享内存替代线程私有的大数组。

05 · 统一内存入门

从 CUDA 6.0 开始，NVIDIA 引入了统一内存（Unified Memory, UM）：用 cudaMallocManaged() 分配一段 CPU 和 GPU 都能直接访问的内存，你不再手动 cudaMemcpy，系统按需迁移数据。

#include <cuda_runtime.h>
#include <stdio.h>

int main() {
    int n = 1 << 20;
    size_t bytes = n * sizeof(float);
    float *a, *b, *c;
    cudaMallocManaged(&a, bytes);
    cudaMallocManaged(&b, bytes);
    cudaMallocManaged(&c, bytes);

    for (int i = 0; i < n; i++) { a[i] = i * 1.0f; b[i] = (n - i) * 1.0f; }

    int blockSize = 256;
    int gridSize = (n + blockSize - 1) / blockSize;
    vecAdd<<<gridSize, blockSize>>>(a, b, c, n);
    cudaDeviceSynchronize();      // 等待 GPU，再在 Host 上读结果

    cudaFree(a); cudaFree(b); cudaFree(c);
    return 0;
}
什么时候用统一内存？ 它非常适合原型开发与不规则访问（树、图、稀疏结构），能省去繁琐的手动管理。但在追求极致性能时，page fault 处理的开销可能不可接受；而 CPU 多线程访问 UM 需要格外小心——多个 CPU 线程同时改写 UM 数据可能引发数据竞争。

06 · 常见内存错误

内存相关的 bug 在 CUDA 里最常见，也最难查。下面是一个典型场景：用 cudaMallocManaged 分配粒子位置数组，Host 端一个线程写、Device 端并行读写。程序“看起来”正常，结果却总在边缘上偏差。根因是数据竞争——CPU 的写与 GPU 的读可能同时发生（经由 page fault 机制），GPU 读到的是更新到一半的数据。

这正是 UM 在 CPU 多线程场景下的经典陷阱：页粒度是 4KB，若 CPU 与 GPU 同时访问同一页内的不同位置，硬件无法提供一致性保证。常见修复是用 cudaMemAdvise() 与 cudaMemPrefetchAsync() 显式引导数据放置与迁移，或干脆回到手动 cudaMalloc/cudaMemcpy。

非法内存访问（Illegal Memory Access）最“无声”。 它往往不立即崩溃，而是在你完全没料到的时候抛出一个莫名其妙的错误。常见触发：数组越界、未初始化指针、释放后使用。更糟的情况是越界写到别的有效数据上——程序照常跑、结果却错，还不给任何提示。所以两条纪律要刻进习惯：每个内存访问都核对边界，每次 CUDA API 调用都检查返回值。

到这里，内存模型的全局图景已经铺开：从最快的寄存器到最慢的全局内存、从合并访问到统一内存、再到典型陷阱。但有一种内存我们只点了名——共享内存。它是 CUDA 性能优化的核心，值得用一整章来展开，这就是下一章。
